## 9 項逐項分析

### 1. 發布排程（草稿到時間自動上下線）

**問題場景**：編輯者寫好新聞、政策後，希望指定未來某時間上線（例如政策修法生效日同步上架），或設定下架時間（過期活動自動隱藏）。目前 PageManagement 已有「開始/結束發布時間」UI，但無法確認後端是否真的有排程 worker 在跑。

**對應 xlsx**：部分 #58 審稿（覆蓋發布觸發），新增子項建議。

**建議方案**：
- DB：每個內容 model（News / Article / Policy）加 `publishAt` / `unpublishAt` 兩個 nullable timestamp
- 後端：cron job 每 5 分鐘掃描，將到達 `publishAt` 的草稿狀態改 published、到達 `unpublishAt` 的 published 改 unpublished
- 前端：編輯頁明確顯示「下次自動切換時間」+ 該內容當前實際狀態
- 補充：失敗回退機制（時間到了但 publishAt < createDate 之類異常）

**技術重點**：
- 後端排程 worker（IIS Web Job 或獨立 console + Windows Task Scheduler）
- DB index 在 publishAt / unpublishAt 加速掃描
- audit log 記錄每次自動切換動作

**依賴**：無強相依，可獨立做，但建議跟 #9 審核流程一起設計（核准後也是排程上線同條路徑）

**估時**：前端 1.5 day / 後端 2-3 day / DB schema 0.5 day

**風險**：cron 失效 → 內容沒按時上下線，建議加監控告警

---

### 2. 內容到期提醒（政策過期、新聞太久沒更新）

**問題場景**：福利政策有效期通常有時限（例如 2026 年度補助方案），過期後若忘記下架會誤導民眾；新聞發布超過 90 天可能資訊過時但仍掛在首頁。

**對應 xlsx**：#59 內容健康檢查中心（涵蓋此項，建議拆出獨立子項）。

**建議方案**：
- DB：每個內容 model 加 `expireAt` nullable + `lastReviewedAt` timestamp
- 後端：cron job 每天凌晨掃描，產生「待提醒清單」
- 前端 Dashboard：新增「即將到期 / 久未更新」widget，列當週需處理項目
- 通知：email 給負責人（或先做站內通知中心，#60 通知中心相關）

**技術重點**：
- 共用 #8 健康檢查的同一套定期掃描架構
- 提醒規則設定化（不同 model 不同閾值：政策 90 天前提醒、新聞 60 天前）

**依賴**：建議跟 #8 健康檢查同時做（共用掃描排程），跟 #60（既有 xlsx）通知中心串接

**估時**：前端 1 day / 後端 2 day（含通知整合）

**風險**：低 —— 即使失效也不影響線上資料，只是少了提醒

### 3. 差異比對（diff，編輯前後內容 diff）

**問題場景**：審核者要核准一筆修改時，希望快速看「這次改了什麼」，不必前後比對整篇全文。

**對應 xlsx**：#51 重要變更歷史（版本/diff）—— 已記。

**建議方案**：
- DB：每次儲存時建立 `content_snapshot` table 記錄完整內容 JSON（或欄位粒度）
- 前端：編輯頁 / 詳情頁加「歷史版本」tab，並排顯示前後差異（用 `diff-match-patch` 或 `jsdiff`）
- 視覺：刪除紅底刪除線、新增綠底、修改 inline 標示

**技術重點**：
- snapshot 儲存策略：每次儲存都存（簡單但浪費空間）vs 只記 diff（節省但難回復）—— 建議每次儲存完整 JSON，配合 #4 版本回復
- DB 設計：`content_snapshot { id, modelType, modelId, snapshotJson, createdBy, createdAt }`
- 大型內容（PageManagement 整個 sections JSON）的 diff 演算法選擇

**依賴**：#4 版本回復的基礎（同一份 snapshot 既能 diff 也能 restore）

**估時**：前端 3 day（含 UI） / 後端 2 day / DB 0.5 day

**風險**：snapshot 累積大 → 需設定保留策略（如保留最近 30 個版本 + 每月一個）

---

### 4. 版本回復（誤改回上一版）

**問題場景**：編輯不小心覆寫了重要欄位，希望一鍵回到上一版本，不用手動重打。

**對應 xlsx**：#51 + #52 軟刪除 + 30 天復原 —— 已記。

**建議方案**：
- 基於 #3 的 snapshot table
- 前端：「歷史版本」tab 每個版本旁加「還原」按鈕，點擊後 confirm dialog → 將 snapshot 內容寫回主表
- 後端：還原行為本身也建立一個新 snapshot（避免再次 undo 時找不到當前狀態）

**技術重點**：
- 還原 = 新增 snapshot + 覆寫主表，不是「直接切換版本」（避免 race condition）
- 配合 audit log 記錄「誰、何時、從哪個版本還原」
- 與軟刪除（#52）打通：刪除的內容也能在 30 天內還原

**依賴**：強相依 #3（必須先有 snapshot 機制）

**估時**：前端 1 day（UI 簡單）/ 後端 1 day（含 audit 整合）

**風險**：使用者誤點還原 → 必須 confirm dialog + 顯示 diff 預覽再執行

### 5. 批次匯入 / 匯出（政策、QA、代碼表用 Excel）

**問題場景**：代碼表 / FAQ 一次要新增 50 條時，逐筆從後台輸入太慢；月報要把所有政策匯出 Excel 給主管。

**對應 xlsx**：#42 表格批次 + #54 匯入匯出進度。

**建議方案**：
- 匯出：列表頁加「匯出 Excel」按鈕（依當前篩選條件），用 `exceljs` / `xlsx` 在後端生成
- 匯入：上傳 Excel → 後端驗證（欄位、必填、格式）→ 預覽前 10 筆 → 確認後寫入
- 進度：大檔案匯入用 SignalR / WebSocket 推送進度（或前端 polling）
- 範本：每個模組提供 Excel 範本下載

**技術重點**：
- 匯入驗證：必須 dry-run 預覽，避免一鍵寫入 500 筆髒資料
- 失敗處理：第 247 筆失敗時，前 246 筆要 rollback 還是 keep？建議 transaction 全失敗或全成功
- 大檔案：分批處理 + 進度條（與 #54 共用）

**依賴**：無強相依，可獨立做。但建議跟 #54 一起（共用進度條 UI）

**估時**：前端 2 day / 後端 3 day / 每個模組增量 0.5 day

**風險**：使用者匯入錯誤格式造成資料污染 → dry-run 預覽是必須

### 6. 圖片資產中心強化（找重複、檢查尺寸、補 alt）

**問題場景**：後台累積大量圖片但沒人管理，重複上傳浪費空間、巨大圖片拖慢前台、缺 alt 影響 SEO 與無障礙。

**對應 xlsx**：#11 圖片管理 + #61 媒體資產治理中心 —— 已記。

**建議方案**：
- 重複偵測：上傳時計算 file hash（SHA-256），比對既有資料庫，相同則提示「已有相同圖片，是否沿用」
- 尺寸 / 大小檢查：上傳時自動分析（width / height / fileSize），標記超過閾值（>2MB 或 >2000px）
- alt 補完工具：圖片管理列表新增 filter「缺 alt」，批次補 alt
- 引用追蹤：每張圖片顯示「被引用 N 次 / 來自哪些頁面」

**技術重點**：
- file hash 計算與索引（後端上傳時 hash + DB 加 index）
- 引用追蹤需後端在每次內容儲存時掃描 img src 建立關聯表
- 客戶端壓縮（可選）：上傳前用 `browser-image-compression` 客戶端壓縮，省頻寬

**依賴**：與 #8 健康檢查連動（失效圖片掃描）

**估時**：前端 3 day / 後端 4 day（含引用追蹤）

**風險**：引用追蹤掃描成本，建議用 background job 而非每次儲存即掃

### 7. 自動內鏈建議（上稿時提示可連到既有政策、文章、QA）

**問題場景**：寫新文章時，若提到「老人福利」應該連到對應政策頁，但編輯者要自己記得 + 手動找連結。

**對應 xlsx**：**無記錄** —— 本次新增建議。

**建議方案（PoC 等級）**：
- 編輯時偵測文章內提到的關鍵字（例如「老人福利」「身心障礙」）
- 與既有政策 / 文章 / FAQ 標題或關鍵字比對，suggest 可加超連結的位置
- 編輯者點「建議」即可一鍵加 hyperlink

**技術重點**：
- 第一版：純前端關鍵字字典比對（從現有內容抽 title + keyword 建字典）
- 進階：BM25 / TF-IDF 語意相似度（後端做）
- 進階+：用 Gemini API 自動產內鏈建議

**依賴**：無，但前端關鍵字字典需先盤點現有內容

**估時**：純前端 PoC 2 day / 加後端語意比對 +3 day / 加 LLM +2 day

**風險**：低 —— 是「建議」非「強制」，誤判不影響正確性。但若建議品質差會被棄用

### 8. 內容健康檢查（空欄位、斷連結、失效圖片、日期錯誤）

**問題場景**：後台內容隨時間品質下降 —— 連結變 404、圖片被刪、必填欄位空白、發布日期早於建立日期。

**對應 xlsx**：#59 內容健康檢查中心 —— 已記。

**建議方案**：
- 健康檢查 Dashboard：列出所有問題項目 + 嚴重度 + 修復 CTA
- 檢查項目：
  - 空欄位（必填卻空）
  - 外部連結 HEAD 請求驗證（HTTP 200 / 4xx / 5xx / timeout）
  - 圖片 src 對應檔案存在性
  - 日期邏輯（publishAt < unpublishAt、不晚於 expireAt）
  - 重複 slug
- 排程：cron 每天凌晨掃描，結果存 `content_health_log` table

**技術重點**：
- 外部連結驗證要 throttle（不要 DDoS 對方）
- 與 #2 到期提醒共用同套掃描排程
- 結果 UI：問題清單 + 「跳到該內容修復」直連

**依賴**：與 #2 共用排程架構，與 #6 共用圖片有效性檢查

**估時**：前端 2 day / 後端 3 day（含排程）

**風險**：低，純讀取無破壞性。但掃描成本要控制（incremental 而非 full scan）

### 9. 審核流程（草稿、送審、退回、發布）

**問題場景**：多人協作時，編輯者寫稿後主管要審核才能發布；目前狀態只有「草稿 / 已發布 / 已下架」三個，無「待審 / 退回」中間態。

**對應 xlsx**：#58 審稿指派與 SLA 提醒 —— 已記。

**建議方案**：
- 狀態流：`draft → pending_review → (approved → published) | (rejected → draft)`
- DB 新增：`reviewer` 欄位、`reviewedAt`、`rejectReason`
- 前端：草稿按「送審」→ 主管在 Dashboard 看「待我審」清單 → 並排 diff（用 #3）後 approve / reject
- 通知：送審時 email / 站內訊息給審核者，退回時通知作者
- SLA：超過 N 小時未審核自動提醒（與 #2 到期提醒共用）

**技術重點**：
- 狀態機設計（必須單向流轉，避免「已發布」回到「草稿」造成版本混亂）
- 與 #1 發布排程串接（approved 自動 publish 或排程到指定時間）
- 與 #3 diff 串接（審核畫面必看 diff）
- 與 audit log 串接

**依賴**：強相依 #3 diff（審核要看 diff）、可選串接 #1 發布排程

**估時**：前端 4 day / 後端 4 day / DB 1 day

**風險**：流程改動影響所有編輯工作流，建議分模組逐步開（例如先 News，再 Policy）

**這波結束時**：完整內容生命週期管理 —— 從建立、審核、發布到健康監控。

### 第三波（進階，3-4 sprint）

| 項 | 估時 | 為什麼最後 |
