# iFare GA4 後台同步規劃（2026-05-12）

> 本文件為 **規劃文件**，目的在於確認 iFare 是否要把 GA4 分析資料同步顯示於後台，以及應如何設計成「穩定、可維護、不容易打爆伺服器」的方案。本文先描述建議架構，不代表已完成正式串接。

## 摘要

- **可以做**：GA4 的分析結果可以同步顯示在 iFare 後台。
- **建議做法**：不要讓後台頁面每次載入都直接打 GA4 API，改成 **背景排程同步 + 資料庫快取 + 後台讀快取**。
- **資料庫建議**：需要存，但只存 **後台要顯示的整理後結果**，不建議一開始就存 GA4 全量原始事件。
- **更新頻率建議**：
  - 一般情境：每 `60` 分鐘同步一次
  - 活動 / 廣告追蹤期：每 `30` 分鐘同步一次
- **正式環境優先建議**：若網站跑在 `IIS / Windows Server`，建議由 **Windows Task Scheduler** 觸發同步，不建議只靠網站自己在背景一直跑。

---

## 目標

本功能的目標不是取代 GA4 後台，而是讓 iFare 管理後台可以直接看到：

- 近 7 / 28 / 90 天流量摘要
- Active Users / Sessions / Conversions 等 KPI
- 流量來源分布
- 熱門頁面排行
- 裝置分布
- 基本趨勢圖
- 最後同步時間

這樣管理者不需要每次都另外登入 GA4，也能在既有後台流程中快速看營運數據。

---

## 為什麼不要即時查 GA4

如果後台每次開頁都即時查 GA4，會有幾個問題：

1. **頁面變慢**
   - 後台必須等待外部 API 回應，載入時間容易不穩定。
2. **多人同時開頁會重複打 API**
   - 同一份報表被重複查詢，沒有必要。
3. **容易碰到配額限制**
   - GA4 Data API 有 property quota、hourly quota、concurrent request 限制。
4. **外部服務異常時後台也會被拖累**
   - GA4 或網路暫時有問題，後台分析頁就可能卡住。

因此建議將「查 GA4」和「顯示後台」拆成兩件事：

- 查 GA4：背景排程處理
- 顯示後台：讀本地資料庫快取

---

## 建議架構

```text
GA4 Data API
    ↓
GA4 同步程式 / 排程工作
    ↓
iFare 資料庫快取表
    ↓
iFare Backend API
    ↓
iFare 後台分析頁
```

### 資料流說明

1. 排程工作固定時間執行
2. 向 GA4 Data API 查詢指定報表
3. 將整理後的資料寫入 iFare 資料庫
4. 後台分析頁讀取 iFare Backend API
5. Backend API 直接回傳本地快取資料，不即時打 GA4

---

## 是否需要存資料庫

### 結論

**需要存資料庫，但存的是整理後的快取資料，不是 GA4 全量事件明細。**

### 建議存的資料

- KPI 摘要
- 日別 / 月別趨勢
- 熱門頁面排行
- 流量來源分布
- 裝置分布
- 同步執行紀錄
- 最後同步時間

### 不建議一開始就存的資料

- GA4 全量事件 raw data
- 所有使用者層級明細
- 極細粒度歷史維度拆解資料

### 原因

- 後台看板通常只需要「摘要」與「排行」
- 快取資料量小、查詢快、維護簡單
- 避免資料表膨脹太快
- 降低之後資料同步與清理成本

以下為第一版可行結構，實際欄位名稱可依現有命名規範調整。

## 建議同步頻率

### 預設值

- **每 60 分鐘** 同步一次

適合：

- 一般內容型網站
- 主管查看週 / 月趨勢
- 日常營運觀察

### 加密模式

- **每 30 分鐘** 同步一次

適合：

- 廣告投放期
- 活動頁觀察期
- 需要比較快看到變化時

### 不建議

- 每分鐘同步
- 每次開頁同步
- 每位管理者各自觸發一份即時查詢

---

## 建議觸發方式

### 方案 A：Windows Task Scheduler 觸發同步

**最推薦**，尤其是正式環境若跑在 `IIS / Windows Server`。

做法：

1. 建一個可執行同步的程式或受保護的內部 API
2. 由 `Windows Task Scheduler` 每 30 或 60 分鐘呼叫一次
3. 同步完成後寫入資料庫快取

優點：

- 不依賴網站是否被喚醒
- 不怕 IIS App Pool 回收造成排程失效
- 維運方式明確

### 方案 B：網站內部背景工作

可做，但 **不建議當第一選擇**。

風險：

- IIS 閒置回收後可能不準時
- 站台重啟時排程中斷
- 維運追查相對麻煩

### 方案 C：手動按鈕觸發

建議只作為輔助，不作為主要同步方式。

可在後台加一個：

- `手動更新 GA4 資料`

但要限制：

- 至少間隔 `10` 分鐘才能再更新一次
- 若已有同步工作進行中，不允許重複觸發

---

## 後台頁面行為建議

後台分析頁建議行為如下：

1. 頁面開啟時，只讀本地快取資料
2. 顯示 `最後同步時間`
3. 若快取不存在，顯示：
   - `尚未同步 GA4 資料`
4. 若同步失敗，顯示：
   - `資料同步失敗，請稍後重試或通知管理員`
5. 若管理者按下手動更新：
   - 只觸發同步任務
   - 頁面先顯示既有快取
   - 不要讓使用者一直等待外部 API 回應

## 與現有專案結構的對應

目前專案已有舊版站內流量分析結構：

- 後台前端分析頁：
  - `Dev/Dev Code/iFare_Backend/src/views/Analysis/Analysis_DashboardView.vue`
- 後台 API：
  - `Dev/Dev Code/iFare_Backend_API/src/IFare_BDAPI.Application/Visitor/VisitorAppService.cs`
- 分析資料整理：
  - `Dev/Dev Code/iFare_Backend_API/src/IFare_BDAPI.Core/TaskManager/Visitor/VisitorTaskManager.cs`

因此 GA4 正式版建議採用同樣分層方式，新增一套獨立模組，不要直接把 GA4 邏輯硬塞進既有 `Visitor` 模組。

### 建議新增模組

- `Ga4AppService`
  - 後台 API 對外入口
- `IGa4AppService`
- `Ga4SyncTaskManager`
  - 專門向 GA4 抓資料與整理
- `IGa4SyncTaskManager`
- `Ga4CacheTaskManager`
  - 專門讀寫快取表
- `IGa4CacheTaskManager`

這樣可把責任切清楚：

- AppService：提供 API
- SyncTaskManager：向外部 GA4 取資料
- CacheTaskManager：管理 DB 快取

## 排程實作流程建議

### 每次同步應做的事

1. 建立同步 log，記錄開始時間
2. 依需求向 GA4 取以下資料：
   - KPI summary
   - 趨勢圖
   - 熱門頁面
   - 流量來源
   - 裝置分布
3. 將資料整理成後台需要的格式
4. 刪除舊快取或覆蓋同區間快取
5. 寫入新快取
6. 更新同步 log 為成功
7. 若失敗，紀錄錯誤訊息

### 實務建議

- 同步工作應包 transaction 或明確分段，避免寫一半資料
- 同步完成前，不要先刪光舊資料
- 可採用「新資料寫完再替換」策略，避免頁面讀到半套資料

## 權限與安全

### 不應做的事

- 前端直接帶金鑰呼叫 GA4 API
- 把 service account 憑證放到前端
- 讓一般使用者無限制重複觸發同步

### 建議做法

- 由後端保管 GA4 憑證
- 同步行為只在後端執行
- 手動同步 API 只開給特定角色
- 記錄所有同步操作 log

---

## 風險與注意事項

### 1. GA4 配額限制

GA4 Data API 有 quota，不能無限制打。

根據 Google 官方文件，目前標準 property 的 Core quota 包含：

- 每 property 每日 `200,000` tokens
- 每 property 每小時 `40,000` tokens
- 每 project / property 每小時 `14,000` tokens
- 每 property 同時併發 `10` 個請求

但 quota 消耗量會依查詢複雜度改變，因此不應只看固定次數。

### 2. 不要一次查太多維度 / 太長日期

GA4 Data API 的 token 成本會受以下因素影響：

- rows 太多
- columns 太多
- filter 太複雜
- date range 太長

所以第一版建議只做簡單摘要查詢。

### 3. IIS 回收問題

若正式站跑在 IIS，網站內建背景 worker 的準時性不如外部排程穩定。

### 4. API 異常時的降級策略

若 GA4 暫時失敗，後台仍應顯示前一次快取，不要整頁空白。

## 分階段實作建議

### 第一階段：畫面與 API 骨架

- 後台先完成分析頁版型
- Backend API 回傳 mock / cache 結構
- 不接真 GA4

### 第二階段：快取資料表與同步流程

- 建資料表
- 建同步服務
- 建手動同步入口
- 後台改讀快取 API

### 第三階段：正式串接 GA4

- 加入 GA4 service account
- 實作 `runReport`
- 補同步 log / 錯誤處理 / 配額監測

### 第四階段：維運與優化

- 視需求加更多報表
- 增加 campaign/source/medium 拆解
- 規劃更長期歷史資料保留策略

---

## 建議結論

對 iFare 目前情境，建議採用以下方案：

1. **需要存資料庫**
   - 但只存後台展示用的快取結果
2. **預設每 60 分鐘同步一次**
   - 活動期再改成 30 分鐘
3. **正式站優先用 Windows Task Scheduler**
   - 比網站內部背景排程穩定
4. **後台只讀快取**
   - 不即時打 GA4
5. **保留手動同步**
   - 但要有限流與權限控管

## 後續建議

若確認要做，下一步建議依序進行：

1. 確認資料表結構
