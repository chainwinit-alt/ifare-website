# AI 摘要「問答」模型測試工具

這組腳本測的是 **AI 摘要的追問問答**（`answer` / `guidance` 模式），**不是**首次搜尋的總覽（`overview` 模式）。

這個區分很重要。2026-08-20 那次模型比較只測了搜尋總覽，結論是「120b 全面優於 20b，20b 留第二順位」——那個結論在總覽上仍然成立，但**總覽測不出問答的問題**。`openai/gpt-oss-20b` 在「網站查無資料」時會自行編造應備文件清單，這個行為只在追問問答時出現，因此躺了四天沒被發現。

換模型、改提示詞、調整候選鏈之後，都應該跑一次這裡的腳本。

## 前置條件

| 需要什麼 | 位址 | 備註 |
| --- | --- | --- |
| Nuxt dev server | `http://localhost:3000` | `npx nuxi dev`。改過 `server/` 下的檔案或 `nuxt.config.ts` 要重啟，HMR 不涵蓋 |
| 政策 API | `http://localhost:8082/api/services/app` | 注意沒有 `/ifare_api` 路徑前綴。不在 IIS 下、開機不會自動起來 |

`.env` 裡的 `NUXT_FRONTEND_API_SERVER_BASE` 要指向上面那個政策 API，否則 `enrichSummaryCases` 補不到政策明細，模型會拿到殘缺的輸入。

## 怎麼指定模型

全部走 `POST /api/llm/summarize/stream`，payload 帶三個關鍵欄位：

```jsonc
{
  "provider": "groq",              // 或 "gemini"
  "model": "openai/gpt-oss-120b",  // 指定型號
  "refresh": true                  // 跳過伺服器端快取
}
```

三件事必須知道，否則測出來的結論會是反的：

1. **指定 `model` 之後不做候選退讓。** 這是刻意的——比較模型時最怕「以為在測 A，其實 A 掛了退到 B」。指定的模型失敗就直接失敗，看得見才修得掉。
2. **指定型號會用獨立的快取桶。** 不分開的話，換一個模型重跑會拿回上一個模型寫好的字，兩邊看起來一模一樣，會誤以為模型沒有差別。
3. **一定要帶 `refresh: true`。** 否則同樣的輸入會拿回快取，等於沒有真的測。

指定型號時也不看冷卻時間（撞到 429 的模型會被冷卻 10 分鐘），要測的就是它，被跳過會讓人以為測過了。

**Groq 免費方案有 8000 TPM 上限**，連續測很容易撞到 429。`bench-all.mjs` 內建重試（等待後重試最多 4 次）；其他腳本靠請求之間的 sleep 節流。撞到 429 而沒有重試的話，某個模型會缺一角資料，看起來像「那個模型沒問題」。

## 腳本

跑之前先 `cd` 到這個目錄，腳本用相對路徑讀寫 json。

### `bench.mjs` — 七情境 × 四模型

```bash
node bench.mjs        # → results.json
```

同一筆長照政策（#898）問七道民眾常見問題：應備文件、補助金額、承辦窗口、資格判斷、多筆比較、跨縣市查詢、補充條件。前四題走明細頁「問這筆政策」（`focusPolicy: true`），後三題走搜尋摘要卡追問。

要換模型清單就改檔案最上面的 `MODELS` 陣列。

### `repeat.mjs` — 關鍵題複測三輪

```bash
node repeat.mjs       # → repeat.json
```

只重跑兩題（文件題、跨縣市題），各三輪，用來確認是**穩定行為還是單次噪音**。單次結果不足以下結論——20b 的編造是 3/3 重現才確定的。

### `pick.mjs` — 挑全類別測試的政策

```bash
# all.json 沒有進版控（1.3 MB，可重抓），先抓回來：
curl -s "http://localhost:8082/api/services/app/FarePolicy/GetIFarePolicyList?MaxResultCount=2000&SkipCount=0" -o all.json
node pick.mjs         # → picked.json
```

從 12 個政策類別各挑兩筆代表：一筆 `evidence` 欄位殘缺（測編造），一筆 `qualification` 含審查門檻（測斷定資格）。

⚠️ **文件題的抽樣標準有缺陷，見下方「已知問題」。**

### `bench-all.mjs` — 全類別測試

```bash
node bench-all.mjs    # → results-all.json（需要 picked.json）
```

`picked.json` 裡的每筆政策 × 四個模型。約 92 次呼叫，Groq 的 TPM 限制下要跑 20–30 分鐘，建議放背景。

### `rejudge.mjs` — 重新判定

```bash
node rejudge.mjs      # 就地改寫 results-all.json（需要 sources.json）
```

不重打模型，只用新規則重判已存的輸出。改判定規則時用這個，不必重跑整輪測試。

`sources.json` 是各政策的來源全文，用來比對模型講的內容有沒有出處。要重建的話，對 `picked.json` 裡每個 id 打 `GetIFarePolicyDetail`，把所有字串欄位串起來（記得先 `decodeURIComponent`，`welfareInfo` 存的是 percent-encoded HTML）。

### `verify.mjs` — 驗證 overview 改動

```bash
node verify.mjs
```

檢查首次搜尋摘要的字數與段落結構，以及實際走到哪一個模型。改過 `buildOverviewPrompt` 之後跑這個。

## 三種錯誤類型

主管的判準是資料正確性，而正確性就是這三件事：

| 類型 | 定義 | 判定方式 |
| --- | --- | --- |
| **編造** | 憑空生出網站沒有的內容，還標上 `[參考 N]` 讓人以為有出處 | 比對 `DOC_TERMS`（37 個常見文件名詞）：出現在回答裡但不在來源全文中 → 編造 |
| **斷定資格** | 把「須經評估或審核才能確定」的事說成已經確定 | 拆成句子，找出指涉使用者（您／媽媽）且宣稱符合資格的句子，再看有沒有帶條件（若／經評估／須先） |
| **擋錯人** | 漏讀條件，把符合資格的民眾說成不符合 | **自動規則抓不到**，只能人工核對來源條文 |

「編造」與「斷定」的差別：編造是**憑空生出不存在的資訊**；斷定是**資訊都對，但把不確定的事說成確定**。前者讓民眾備錯文件白跑一趟，後者讓民眾以為一定申請得到，評估沒過才落空。「擋錯人」的傷害是**錯失應得權益**。

## ⚠️ 重要警告：不可直接採用自動判定的數字

`rejudge.mjs` 的規則改過**四輪**，每一輪都還會冒出新的誤判：

| 輪次 | 修掉什麼 | 誤判的例子 |
| --- | --- | --- |
| 1 | 疑問句式、導向洽詢 | 「關於您媽媽**是否符合**資格，建議直接向承辦單位洽詢確認」被判成斷定 |
| 2 | 沒有處理否定 | 「您的 80 歲母親**不符合**申請資格」——正確拒絕——被判成斷定（正則 `(您\|媽媽).{0,12}(符合)` 匹配到「不符合」裡的「符合」） |
| 3 | 異體字 | 來源寫「身**份**證」、模型寫「身**分**證」，語意相同卻被判成憑空生出來 |
| 4 | 條件連接詞不齊 | 「**只要**符合⋯就可以申請」「**必須**⋯**才能**申請」「**若**⋯**則**可申請」仍被判成斷定 |

修到第四輪仍有漏網句式。**最終結論必須逐筆人工看過原文再定案**，自動規則只能當初篩。

這不是小事：第二輪那個 bug 對「傾向給明確答案」的模型（120b 會明確說「不符合」）殺傷最大，不修的話會得出完全相反的結論——一度顯示 120b 斷定 8/11，人工複核後實際是 0/11。

2026-08-24 這次的做法是：自動規則初篩 → 逐筆讀原文 → 把最終判定寫死在產表程式裡。44 筆資格題回答全數人工檢視。

## 已知問題

### `bench-all.mjs` 的文件題測不到編造

`pick.mjs` 挑「測編造」的政策時，用的標準是 **`evidence` 欄位字數最少**。但**字數少不等於沒寫文件清單**——逐筆核對後發現這些政策的欄位雖然只有幾十字，內容卻正是文件清單：

| 政策 | `evidence` 內容 |
| --- | --- |
| #1462 喪葬補助 | 死亡證明書、戶口名簿、身分證、印章 |
| #903 到宅沐浴 | 申請表 |
| #781 青年租屋 | 申請表、郵政儲金簿封面影本 |
| #81 離島健保 | 「不需文件申請」 |

模型照抄就對了，測不到編造。

**真正會誘發編造的是「欄位很長但只寫流程、沒有文件清單」的政策**，例如 #898：`evidence` 有 300 多字，全是申請流程（事前申請、窗口、核定後購置、六個月內完成、送區公所申領），從頭到尾沒有列出應備文件。這種政策反而不會被「字數最少」的標準挑中。

所以 2026-08-24 那輪全類別測試的文件題結果（四個模型皆 0 編造）**不採計**。編造的證據以 `repeat.json`（單一政策 #898 三輪複測）為準。

要修的話，`pick.mjs` 的挑選條件應改成「`evidence` 有內容，但不含 `DOC_TERMS` 裡任何一個文件名詞」。

### 其他限制

- 「會不會編造」目前只有 **1 筆政策** 的證據（#898 × 3 輪），樣本偏薄。
- 未涵蓋芒寶聊天機器人（`chatbot.post.ts` 有自己的候選組裝，吃 `groqModels`）與搜尋意圖判讀（吃 `groqIntentModels`）。
- Gemini 目前不走串流（只有 Groq 實作了 `onDelta`），所以測到的「首字時間」等於「整篇完成時間」，跟 Groq 不能直接比。

## 2026-08-24 結論摘要

四個模型：`openai/gpt-oss-120b`、`openai/gpt-oss-20b`（Groq 平台執行，OpenAI 公開釋出的開放權重模型，非 ChatGPT）、`gemini-3.5-flash-lite`、`gemini-3.1-flash-lite`（Google）。

| 模型 | 編造 | 斷定資格 | 擋錯人 | 結論 |
| --- | --- | --- | --- | --- |
| `openai/gpt-oss-20b` | 會（3/3） | 會（3 次） | 會（1 次） | **不建議使用** |
| `openai/gpt-oss-120b` | 不會（0/3） | 偶發（1 次） | 不會 | 可用，建議加回答規則 |
| `gemini-3.5-flash-lite` | 不會（0/3） | 不會 | 不會 | 可用 |
| `gemini-3.1-flash-lite` | 不會（0/3） | 不會 | 不會 | 可用 |

次數為兩份測試合計（單一政策三輪複測 + 11 個政策類別的全類別測試）。

**具體實例：**

- **編造**（20b，#898）：網站只寫申請流程、沒列任何文件，卻回答「申請時需準備的文件包括：身分證明文件（如身分證、戶籍謄本等）、失能評估報告、輔具使用需求說明、居家無障礙環境改善評估表、補助撥款申請表格⋯」並標上 `[參考 1]`。三輪都發生。
- **斷定**（20b，#1100 危機家庭兒童托育補助）：回答「符合危機家庭條件的任何人（包括您媽媽）皆可申請」。但申請人須為兒童本人、父母、監護人或實際照顧兒童之人，80 歲長輩並不適用。同一題另三個模型都正確指出不適用。
- **擋錯人**（20b，#229 桃園市 65 歲以上老人健保自付額補助）：來源第三項明訂「年滿 65 歲⋯設籍並實際居住滿一年者」，80 歲符合；卻回答「您媽媽的年齡與條件尚未符合」——只讀了前兩項（未滿 70 歲之中低收、百歲以上），漏掉第三項。同一題另三個模型都答對。
- **斷定**（120b，#898）：回答「您符合申請條件，因為年滿 80 歲且符合長照需要等級 2 級以上」。長照等級須經照管中心評估才知道，民眾從未提過。同一模型在全類別測試的 11 個類別中均未再犯，屬偶發不穩定。

**功能面**（答得好不好用，與正確性分開看）：120b 是唯一會把補助比例換算成實際金額的（4 萬／3.6 萬／2.8 萬），也是唯一在多筆比較時給出選擇建議的；兩個 Gemini 寫得較平但最穩定。

**建議：**

1. 將 `openai/gpt-oss-20b` 移出 AI 問答的模型清單。
2. 在回答規則加兩條紅線：須經評估才能確定的資格一律用條件句、不得斷定民眾符合；系統已查到的其他縣市筆數必須寫出來。這對任何模型都生效，日後換模型不必重做。
3. 換模型或改規則後跑一次這裡的腳本。
